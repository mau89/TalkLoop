# День 32 — автоматическое AI-ревью PR

## Что реализовано

Workflow `.github/workflows/ai-review.yml` запускается при открытии PR,
новом коммите, повторном открытии и переводе PR из draft в ready.
Он получает историю Git, точные `base.sha` и `head.sha` события и запускает
`tools/day32/review_pr.py`. Ревью появляется в **Actions → запуск → Summary**
и в скачиваемом артефакте `ai-review-<номер PR>-<попытка>`.
Отдельный комментарий в обсуждение PR не отправляется.

Текст содержит три раздела: потенциальные баги, архитектурные проблемы,
рекомендации. Каждая находка указывает приоритет P1/P2/P3, файл, сторону
diff, изменённую строку, последствие, исправление и связанные источники RAG.
Пустой список находок допустим и не означает, что весь проект проверен.

## Запуск на Mac

Ревью переключено на **self-hosted Mac runner** с меткой `talkloop-review-mac`.
Генерация работает через локальную `qwen3.5:9b-q8_0` в Ollama по адресу
`http://127.0.0.1:11434`. Облачный ключ не требуется, код и diff для генерации
не отправляются в Anthropic. GitHub хранит PR, запускает задание и принимает отчёт.

Workflow принимает PR, созданные владельцем `mau89` из этого же репозитория,
а также ручной запуск владельцем с `base_sha`/`head_sha`. Для fork PR и других
авторов задание не запускается на личном Mac. Дополнительно на самом раннере
установлена проверка до выполнения шагов: репозиторий, workflow, автор PR,
инициатор и отсутствие fork. Изменение условия в PR не отключает эту проверку.

Если Ollama выключена, workflow запускает уже установленное приложение
в фоне. Новые модели не скачиваются: отсутствие Qwen приводит к понятной ошибке.
Mac должен быть включён и не спать. Раннер запускается как пользовательская
LaunchAgent-служба после входа в macOS. Одновременно он выполняет одно задание.

[Установка, влияние на работу, пауза и удаление раннера](day32-mac-runner.md).

## Откуда берётся diff и код

Скрипт вычисляет `merge-base(base, head)` и сравнивает его с head,
как при обычном просмотре изменений PR. Изменения, существующие только
в целевой ветке после расхождения веток, не становятся частью diff PR.
Список файлов читается в NUL-разделённом формате, поэтому поддерживаются
пробелы и кириллица. Переименования и удаления сохраняют старый путь.

Из каждой версии читаются Git blobs; локальные несохранённые и незакоммиченные
правки в ревью не попадают. В LLM передаются полные diff включённых файлов,
номера добавленных/удалённых строк и ограниченные фрагменты кода до/после
изменения. Исходники приложения не собираются и не запускаются анализатором.

## RAG: документация и код

Для каждого запуска строится локальный поисковый индекс по снимку merge base:

- `README.md` и `docs/**/*.md` — документация и договорённости проекта;
- исходники Kotlin/Java/Swift/Python, скрипты и конфигурация в `core`, `app`,
  `server`, `cli`, `tools`, `gradle`, `.github`, а также корневые Gradle-скрипты.

Используется **BM25**: код и документация режутся на окна до 50 строк
с перекрытием 10 строк, идентификаторы CamelCase и snake_case разбиваются
на поисковые слова. Запрос строится из путей и diff. На пакет выбираются
до трёх фрагментов документации и четырёх фрагментов кода. Окна ограничены
по размеру и помечаются при сокращении. У каждого источника есть ID,
путь, строки и тип `docs`/`code`.

Это отдельный RAG для ревью, без загрузки ONNX/E5 и кулинарного корпуса.
Он работает на стандартной библиотеке Python и не требует сервера TalkLoop.
В `context.json` и `batches.json` можно проверить фактически переданные
diff, код, документацию, поисковые оценки и версии Git.

## Лимиты и проверка ответа

Большой PR разбивается на пакеты: максимум четыре пакета,
до 12 файлов на пакет, до 8 000 символов diff одного файла и до 70 000
символов JSON-контекста одного исходного вызова. На пакет разрешён один запрос исправления неверных привязок
(до восьми запросов модели всего). Большие отдельные diff, двоичные файлы,
symlink, submodule, файлы вне разрешённого корпуса и остаток за лимитами
перечисляются как непроверенные. В отчёте явно отмечается частичное покрытие.
Фрагменты полных файлов ограничены; ревью разных пакетов не заменяет
единого анализа всех взаимодействий большого PR.

Модель возвращает JSON по схеме. Перед выводом скрипт проверяет категории,
приоритеты, размеры полей, уникальность находок, существование ID источников
и принадлежность номера строки фактическому diff. Для удалений используется
сторона `old`, для добавлений — `new`. Пути и номера строк в отчёт добавляются
программно. Эти проверки не доказывают смысловую корректность замечаний:
финальное решение остаётся за разработчиком, тесты по-прежнему необходимы.

Workflow использует `pull_request` и `workflow_dispatch`, токен с `contents: read`,
не сохраняет Git credentials в checkout и не использует `pull_request_target`.
Облачных секретов в workflow нет. Ввод модели не содержит инструментов выполнения
команд; текст PR рассматривается как данные. Host hook установлен отдельно
от checkout, поэтому PR не заменяет его своей версией файла.

## Проверка локально

Из корня проекта, Python 3.9+:

```shell
python3 -m unittest discover -s tools/day32 -v
```

Подготовка контекста последнего коммита без API и без расходов:

```shell
python3 tools/day32/review_pr.py --base HEAD^ --head HEAD --prepare-only
```

Ревью конкретных веток через локальную Ollama:

```shell
python3 tools/day32/review_pr.py --base origin/main --head HEAD --provider ollama
```

Локальная Ollama:

```shell
python3 tools/day32/review_pr.py --base HEAD^ --head HEAD --provider ollama --model qwen3.5:9b-q8_0
```

Контрольный пример: создаётся временный Git-репозиторий, в котором PR удаляет
проверку владельца перед чтением приватной истории. В основной проект ошибка
не добавляется. Ожидание не передаётся модели; после ответа проверяются
категория и положение находки. Контроль строки не доказывает корректность
всего текста ревью или качество на реальных PR.

```shell
python3 tools/day32/demo.py --prepare-only
python3 tools/day32/demo.py --provider ollama
```

Основные результаты: `day32-data/review.md`, `review.json`, `context.json`,
`batches.json`, `model-replies.json` (черновики и результат проверки привязок). Контрольный пример: `day32-data/demo/`.
Индексы и результаты локальных запусков исключены из Git.

## Состояние проверки реализации

Пройденные проверки и покрытие реального diff предыдущего дня сохранены в
[day32-validation.json](day32-validation.json). Проверяются Git-снимки,
поиск документации/кода, пакетная обработка, формат запросов провайдерам,
проверка и вывод ответа. Ответы LLM в автотестах подменены контролируемыми JSON.
Подготовка контекста выполнена также на реальном diff Дня 31 и в контрольном
репозитории с удалённой проверкой доступа.

Контрольный PR с удалением авторизации проверен настоящей локальной Qwen;
ожидаемая находка получена и прошла проверку привязки к diff. Первоначальный
черновик содержал замечания на неизменённых строках; теперь для такого ответа
выполняется один запрос исправления, затем строгая проверка повторяется.
Невалидный исправленный ответ не публикуется как успешное ревью.
