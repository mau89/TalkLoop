# День 13. Состояние задачи

## Контракт

`TaskState` — отдельная сериализуемая часть памяти агента:

- `stage` — этап `planning`, `execution`, `validation` или `done`;
- `currentStep` — точная точка, на которой находится работа;
- `expectedAction` — следующее ожидаемое действие;
- `expectedActor` — исполнитель: пользователь, агент или внешняя система;
- `completionCriteria` — проверяемые критерии готовности шага;
- `paused` — признак паузы, не меняющий остальные поля;
- `taskName` — идентичное для всех этапов название активной задачи;
- `revision` — версия для защиты от конкурентных изменений;
- `transitionHistory` — неизменяемый журнал событий и переходов;
- `pendingProposal` — предложение агента, ещё не подтверждённое пользователем.

Разрешён основной путь `planning → execution → validation → done`. Из
`validation` можно вернуться в `execution`, если проверка нашла дефекты. Другие
переходы отклоняются до обращения к модели.

Состояние меняется только типизированными `TaskEvent`: `PLAN_APPROVED`,
`EXECUTION_FINISHED`, `VALIDATION_PASSED`, `VALIDATION_FAILED`, `PAUSED`,
`RESUMED` или `PROGRESS_UPDATED`. У каждого события есть уникальный ID и ожидаемая
ревизия. Точный повтор уже применённого события ничего не меняет; повтор ID с
другими данными и команда к устаревшей ревизии отклоняются. Это защищает от двойного
нажатия и конкурирующих команд внутри одного экземпляра агента.

## Пауза и продолжение

`pauseTask()` атомарно сохраняет весь снимок и блокирует новые обращения к LLM.
`resumeTask()` меняет только `paused`: этап, шаг, ожидаемое действие, диалог,
рабочая память и профиль остаются прежними. Поэтому после перезапуска приложения
агент продолжает с сохранённой точки, а пользователь не повторяет постановку задачи.

Перед каждым ответом состояние добавляется в system prompt как размеченный блок
`task_state`. Агент получает явную инструкцию продолжать с `current_step`, выполнить
`expected_action` и не пересказывать уже пройденные этапы. Значения экранируются и
трактуются как данные, а не команды.

## Предложение перехода агентом

Кнопка «Попросить агента оценить переход» отправляет отдельный структурированный
запрос. Модель сравнивает подтверждённый диалог с критериями готовности и либо
рекомендует остаться на текущем этапе, либо формирует допустимое событие перехода.
Ответ ограничен JSON Schema.

Предложение сохраняется, но само состояние не меняет. Пользователь явно выбирает
«Подтвердить переход» или «Отклонить». При подтверждении снова проверяются ID,
ревизия и допустимость события, поэтому устаревшее предложение не перезапишет
более новое состояние.

## Проверка

Автономные тесты подтверждают:

- допустимый основной путь и возврат `validation → execution`;
- отказ при недопустимом переходе;
- идемпотентность повторного события и отказ при конфликте ID;
- защиту от двух одновременных команд к одной ревизии;
- паузу и продолжение без потери полей на каждом из четырёх этапов;
- блокировку LLM-вызова во время паузы;
- восстановление новым экземпляром агента после каждого этапа;
- передачу восстановленных шага, исполнителя и критериев модели;
- отсутствие перехода до подтверждения предложения агента.

Запуск тестов:

```shell
./gradlew :core:allTests :app:shared:allTests
```

Живой сценарий с паузой, имитацией перезапуска и продолжением:

```shell
./gradlew :cli:day13 -q --console=plain
```

В приложении вкладка «Агент» теперь первая и открывается по умолчанию. Карточка
`Task State Machine` позволяет начать задачу, сохранить текущий шаг, выполнить
только допустимое событие, поставить работу на паузу, запросить рекомендацию агента,
подтвердить её и просмотреть последние записи журнала.
