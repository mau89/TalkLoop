# День 35 — реальная задача: подготовка Android-релиза TalkLoop

## Задача

После ежедневных изменений приходится вручную вспоминать, что вошло в версию,
запускать проверки, собирать приложение, проверять версию и готовить описание.
Ошибки в этом процессе дают устаревший APK, неверные release notes или сборку
со встроенным личным ключом. Финальный проект автоматизирует эту работу для
настоящего репозитория TalkLoop и установленного на Mac Android SDK.

Результат — локальный релизный кандидат: **release APK без подписи и облачного
ключа**, SHA-256, отчёт проверок, черновик release notes, список ручных проверок
и ZIP-пакет. Запуск доступен из вкладки **«Релиз»** в приложении, из терминала Mac
и ручного GitHub workflow. Сборка во всех случаях выполняется на Mac.

## Проверка из приложения

1. Запустите Ollama и обновлённый сервер TalkLoop (`./gradlew :server:run`). Если
   сервер работал до обновления, остановите и запустите его заново.
2. Откройте вторую вкладку **«Релиз»**. По умолчанию стоят версия `1.1.0`, код `2`
   и предыдущий коммит `8d64764`; для пробного прогона они подходят.
3. В **«Адрес Mac и предыдущий релиз»** можно изменить адрес сервера и точку
   сравнения. Android Emulator: `http://10.0.2.2:8080`; iOS Simulator:
   `http://127.0.0.1:8080`; физический телефон: IP Mac в той же сети.
4. Нажмите **«Подготовить релиз»**. Экран опрашивает состояние каждые три секунды,
   показывает этапы, результаты тестов, коммит, release notes и ручные проверки.
5. После завершения доступны **«Скачать ZIP-пакет»** и **«Скачать APK (без подписи)»**.
   Ссылка открывается в браузере устройства; скачивание не устанавливает APK.
   Полный отчёт и последние строки журнала можно развернуть на экране.

Можно выйти на другую вкладку: сервер продолжит работу. При возвращении экран
загрузит последнюю задачу; кнопка **«Обновить результат»** восстанавливает состояние
после потери связи. Готовый результат доступен и после перезапуска сервера.
Незавершённая сборка при остановке сервера помечается прерванной, её нужно запустить
заново. Одновременный второй запуск через приложение возвращает понятную ошибку.
Результаты приложения: `day35-data/app/<ID>/result/`; предыдущие пакеты не перезаписываются.

Серверные маршруты: `POST /api/releases` с `base`, `version`, `versionCode`;
`GET /api/releases/latest`, `GET /api/releases/<ID>` и
`GET /api/releases/<ID>/artifacts/<имя>`. Скачиваются только известные файлы конкретной
сборки; произвольные пути и символические ссылки не выдаются. Сервер рассчитан на
доверенную локальную сеть. Запрос из браузера с `Origin` не запускает сборку.

## Где участвует AI

Локальная Ollama `qwen3.5:9b-q8_0` получает список настоящих коммитов между `base`
и `HEAD`, изменённые пути, фрагменты diff и README/описание архитектуры. Она
составляет понятные release notes и предлагает ручные проверки, связанные с
изменениями. Каждый пункт изменений должен ссылаться на коммит из этого диапазона.
`context.json` сохраняет точные входные данные, `ai-response.json` — ответ модели.

Тесты, параметры APK и контрольную сумму проверяет код пайплайна. AI не выбирает
команды, не исполняет текст из diff и не объявляет проверки успешными. Его текст
остаётся черновиком: корректная ссылка на SHA не доказывает каждое утверждение.

## Запуск на этом Mac

Нужны уже установленные JDK 21 (подходит JBR из Android Studio), Android SDK,
Ollama с `qwen3.5:9b-q8_0`, Python 3.9+ и доступ к зависимостям Gradle. Модель и
SDK пайплайн автоматически не скачивает. Локальная Ollama должна быть запущена.

Сначала зафиксируйте изменения в Git. Пример для версий после дня 33:

```sh
python3 tools/day35/prepare_release.py \
  --base 8d64764 \
  --version 1.1.0 \
  --version-code 2
```

`base` — последний релиз/коммит, от которого считаются изменения, предок `HEAD`.
Диапазон должен содержать 1–100 коммитов. Для следующей публикации используйте
свою версию и `versionCode`, который выше опубликованного. По умолчанию результат
попадает в `day35-data/1.1.0-<время запуска>`. Можно задать `--output` вручную,
но занятый каталог не перезаписывается: для повтора выберите новый.

Пайплайн собирает **только HEAD**, экспортируя его во временную папку через
`git archive`. Незакоммиченные изменения и локальные файлы не попадают в сборку;
их список указан в `ignoredWorkingTreeChanges`. Рабочая папка, текущая ветка и
`secrets.properties` не меняются. Используются существующие кеши зависимостей Gradle/SDK.
Кеш результатов задач отключён, чтобы не ждать его блокировки другим процессом;
число Gradle workers ограничено четырьмя.
Временная копия удаляется после завершения.

## Что выполняется

1. Проверяется диапазон Git; экспортируется зафиксированный код.
2. Запускаются Python-тесты дней 32, 34 и 35. Нулевое число обнаруженных тестов — ошибка.
3. Gradle запускает `:core:jvmTest`, `:server:test`, `:app:androidApp:assembleRelease`.
   XML-результаты тестов обязательны: ошибки и пропущенные тесты блокируют кандидат.
4. Свойства `talkloop.versionName`/`talkloop.versionCode` задают версию;
   `talkloop.distribution=true` исключает чтение личного ключа в Android-сборке.
   Проверяются пустой ключ в сгенерированном BuildConfig, отсутствие узнаваемого
   ключа Anthropic в DEX, manifest APK, release-режим и отсутствие подписи.
5. Только после успешных проверок Ollama создаёт черновик описания и ручные проверки.
6. Сохраняются отчёт и ZIP-пакет кандидата. Состояние `prepared` означает подготовку
   пакета для владельца; `publishingReady` всегда `false`.

В каталоге результата:

- `TalkLoop-<версия>-unsigned.apk` — реальный неподписанный APK;
- `release.json` — SHA коммитов, статусы этапов, тесты, версия и SHA-256 APK;
- `release-notes.md` — черновик AI и чеклист;
- `report.md` — итог и обязательные шаги перед публикацией;
- `context.json`, `ai-response.json` — вход и ответ модели;
- `*.log` — журналы тестов и сборки;
- `TalkLoop-<версия>-candidate.zip` — пакет для передачи владельцу.

При падении проверки результат `blocked`, код завершения `1`, готовый ZIP не
создаётся. При недоступной Ollama успешно собранный APK и журналы сохраняются,
но завершённого пакета с AI-описанием нет. Ошибки не подменяются тестовыми ответами.

## Что остаётся перед публикацией

Неподписанный APK нельзя установить. Нужна подпись вашим ключом, затем проверка
установки и основных сценариев на устройстве. Облачные вкладки без личного ключа
не работают; локальные функции требуют доступного сервера/Ollama и правильных
адресов. Для Google Play дополнительно нужны AAB, ключ/Play App Signing, доступы
к консоли, политика конфиденциальности и материалы магазина.

Пайплайн ничего не публикует, не создаёт тег и не меняет версию исходников.
Обычная личная debug-сборка сохраняет прежнее поведение с `secrets.properties`;
её по-прежнему нельзя распространять. Режим без ключа относится к Android-кандидату.

## GitHub Actions на существующем Mac-раннере

`.github/workflows/prepare-release.yml` принимает `base`, `version`, `version_code`.
Он использует существующий label `talkloop-review-mac`, те же JDK/SDK/Ollama и
загружает пакет или журналы ошибки в Artifacts на 14 дней. Права — `contents: read`.
Запуск ручной, только владельцем; PR и форки этот релизный процесс не запускают.
Хостовая политика `tools/day32/runner_guard.py` разрешает именно этот workflow и
существующее ревью, сохраняя проверку владельца и события.

При уже установленном раннере актуальную политику можно обновить без переустановки:

```sh
cp tools/day32/runner_guard.py ~/.local/share/talkloop-runner-policy/runner_guard.py
```

Кнопка **Run workflow** появляется после попадания workflow в default branch;
после этого можно выбрать ветку для сборки. Это [требование GitHub](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).
До объединения веток полностью доступен локальный запуск выше. Слияние в `main`
и публикация релиза не входят в этот запуск.

На этом Mac политика раннера уже обновлена. Прежняя версия сохранена рядом как
`runner_guard.before-day35.py`; её можно скопировать обратно в `runner_guard.py`,
чтобы снова разрешить только ревью. Для отключения локального пайплайна достаточно
перестать запускать команду: отдельной службы или расписания для него нет.

## Проверка реализации

```sh
python3 -m unittest discover -s tools/day35 -v
python3 -m unittest discover -s tools/day32 -v
```

Тесты проверяют отказ при упавших/необнаруженных тестах, неверных версиях,
поддельных ссылках модели, чужом workflow, недоступной Ollama и недопустимом APK.
Полный прогон использует настоящие Gradle, Android build-tools и локальную модель;
его сводка сохраняется в `docs/day35-validation.json`.

## Фактический результат на Mac

Кандидат `1.1.0` / `versionCode=2` собран из коммита `2d03cfaef71b` относительно
`8d64764358b2`: 215 Kotlin-тестов и 58 Python-тестов прошли, сборка release успешна.
В `day35-data/1.1.0-candidate/` находятся APK размером около 35 МБ и ZIP-пакет;
проверены целостность ZIP, SHA-256 APK, manifest, отсутствие подписи и облачного ключа.
Это полный локальный прогон; запуск GitHub workflow до объединения с default branch не выполнялся.

[Сводка проверки](day35-validation.json) содержит SHA и статусы.
[Пример release notes после проверки Codex](day35-release-notes.md) показывает
настоящий результат модели с исправленной ссылкой на коммит. Исходные `ai-response.json`
и `release-notes.md` в локальном результате и ZIP оставлены без изменений:
проверка формата и принадлежности SHA диапазону не проверяет смысл утверждения.
