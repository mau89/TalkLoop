This is a Kotlin Multiplatform project targeting Android, iOS, Server.

* [/app/iosApp](./app/iosApp/iosApp) contains an iOS application. Even if you’re sharing your UI with Compose Multiplatform,
  you need this entry point for your iOS app. This is also where you should add SwiftUI code for your project.

* [/app/shared](./app/shared/src) is for code that will be shared across your Compose Multiplatform applications.
  It contains several subfolders:
  - [commonMain](./app/shared/src/commonMain/kotlin) is for code that’s common for all targets.
  - Other folders are for Kotlin code that will be compiled for only the platform indicated in the folder name.
    For example, if you want to use Apple’s CoreCrypto for the iOS part of your Kotlin app,
    the [iosMain](./app/shared/src/iosMain/kotlin) folder would be the right place for such calls.
    Similarly, if you want to edit the Desktop (JVM) specific part, the [jvmMain](./app/shared/src/jvmMain/kotlin)
    folder is the appropriate location.

* [/core](./core/src) is for the code that will be shared between all targets in the project.
  The most important subfolder is [commonMain](./core/src/commonMain/kotlin). If preferred, you
  can add code to the platform-specific folders here too.

* [/server](./server/src/main/kotlin) is for the Ktor server application.

### Running the apps

Use the run configurations provided by the run widget in your IDE's toolbar. You can also use these commands and options:

- CLI (разговорный прогон с LLM): положите ключ в `secrets.properties` (см. `secrets.properties.example`)
  или `export ANTHROPIC_API_KEY=...`, затем `./gradlew :cli:run -q --console=plain`
- CLI-демо Дня 2 (первый подход, до переезда в UI): `./gradlew :cli:day2 -q --console=plain`
- CLI-демо Дня 3 (одна задача четырьмя способами рассуждения): `./gradlew :cli:day3 -q --console=plain`
  — другую задачу выбирает номер: `--args=2`
- CLI-демо Дня 4 (один запрос с temperature 0, 0.7 и 1.2): `./gradlew :cli:day4 -q --console=plain`
  — прогонов на температуру: `--args=5`
- CLI-демо Дня 5 (один запрос на слабой, средней и сильной модели): `./gradlew :cli:day5 -q --console=plain`
  — сверка с эталоном необязательна: `--args=8`
- День 6 (первый агент): запустите Android/iOS-приложение и откройте вкладку «Агент».
  `TalkLoopAgent` принимает реплику, хранит контекст диалога и вызывает LLM через `LlmClient`;
  Compose-экран только отображает запрос, состояние загрузки и полученный ответ.
- День 7 (сохранение контекста): вкладка «Агент» записывает подтверждённые пары реплик в JSON.
  Закройте приложение после ответа агента, запустите снова и спросите о факте из прошлого диалога —
  история восстановится автоматически. Кнопка «Создать нового агента» начинает диалог заново.
- Android app: `./gradlew :app:androidApp:assembleDebug` — ключ берётся из того же `secrets.properties`
  и вкомпилируется в APK, поэтому собранное приложение никому не раздавать; для этого понадобится
  прокси через `:server`
- Server: `./gradlew :server:run`
- iOS app: open the [/app/iosApp](./app/iosApp) directory in Xcode and run it from there.
  Ключ подставляется в сгенерированный `Secrets.kt` из того же `secrets.properties`,
  что и на Android, и так же вкомпилируется в сборку — раздавать её нельзя.

### Вкладка «Формат» — детерминированность ответа

В приложении пять вкладок: «Разговор» (репетитор английского), «Формат» —
лаборатория, на которой отрабатывается управление форматом ответа, — «Мышление»,
где сравниваются способы думать над одной задачей, «Температура» и «Модели».

Роль модели там одна во всех режимах: **автомобильный эксперт**, который отвечает
только про автомобили, а на «какая сегодня погода» коротко отказывает. Меняется
только то, чем задан формат. Один и тот же вопрос уходит 1, 3 или 5 раз подряд —
так видно, стабилен формат или совпал случайно.

| Режим | Чем задан формат | Что получается |
|---|---|---|
| Без ограничений | ничем | обычный текст, парсить нечем |
| Строгие блоки, текстом | системный промпт | обычно соблюдается, гарантии нет |
| JSON просьбой | системный промпт | ломается на markdown-обёртке и преамбуле |
| JSON схемой | `output_config.format` | схему проверяет API |

Схема разбивает машину на шесть фиксированных узлов — двигатель, трансмиссия,
подвеска и рулевое, тормоза, кузов и салон, электроника. Набор зашит в схему
обязательными полями, поэтому любая машина описывается одинаково и две модели
можно сравнивать построчно.

Отказ встроен в ту же схему полем `answerable`: на вопрос не про автомобили
приходит `answerable: false` с причиной, а блок узлов отсутствует вовсе. Так отказ
остаётся машиночитаемым и не ломает формат — под жёсткой схемой модель физически
не может ответить свободным текстом.

Длина настраивается двумя независимыми регуляторами, потому что рычаги разные:
`max_tokens` (100…2000) режет вслепую — ответ обрывается на полуслове и дальше
непригоден, что бы ни показала проверка формата; лимит словами (20…200) уходит
просьбой в системный промпт, и модель округляет его в свою пользу.

Стоп-слова вписываются вручную, через запятую. Это страховка от лишних токенов:
генерация обрывается ровно на слове, как только модель его напишет, само слово в
текст не попадает, а срабатывание видно в `stop_reason` (`stop_sequence` вместо
`end_turn`) и в поле `stop_sequence` — какое именно слово сработало.

Типичный случай — вежливый хвост, за который платишь: поставь `Если у тебя` или
`В заключение`, и предложение помощи в конце ответа просто не будет сгенерировано.

Отдельный тумблер «Просить дописать стоп-слово» превращает его из страховки в
маркер конца: слово добавляется в системный промпт. Под JSON-схемой такой просьбы
не даём — схема запрещает текст вокруг JSON, поэтому слово там не сработает
никогда (сами стоп-слова всё равно уходят в запрос, чтобы это было видно).

Прогон можно оборвать: пока идёт батч, кнопка становится «Стоп», а поля и
переключатели остаются живыми — можно готовить следующий запрос, не дожидаясь
конца текущего. Остановка отменяет корутину, ktor рвёт HTTP-соединение, уже
собранные прогоны остаются, и вердикт пишет «остановлено вручную: N из M».
Оставшиеся запросы не уходят вовсе — на них деньги не тратятся.

Схема, промпты и проверки формата живут в
[ResponseFormat.kt](core/src/commonMain/kotlin/com/mau89/talkloop/llm/ResponseFormat.kt)
и покрыты тестами без обращения к сети.

### Вкладка «Мышление» — четыре способа рассуждения

Здесь меняется не формат ответа, а ход мысли. Одна и та же задача уходит в модель
четырьмя способами подряд:

| Способ | Что в системном промпте | Запросов |
|---|---|---|
| Прямой ответ | ничего | 1 |
| Пошагово | «раздели на шаги, проверяй каждый промежуточный результат» | 1 |
| Промпт от модели | промпт, который модель написала себе сама под эту задачу | 2 |
| Совет экспертов | аналитик, инженер и критик по очереди, у каждого свой вывод | 1 |

Задача берётся с одним проверяемым ответом, и это главное решение вкладки.
Сравнивать «качество рассуждения» на глаз бессмысленно: убедительно выглядят все
четыре ответа, в том числе тот, что привёл к неверному числу. Поэтому ответ
вытаскивается из текста маркером `ОТВЕТ:` и сверяется с эталоном программой,
а способ оценивается долей верных ответов на нескольких прогонах.

Чтобы сравнивались способы, а не мои настройки, всё остальное у режимов одинаково:
условие уходит пользовательским сообщением слово в слово, `max_tokens` один на всех
(выбран по самому прожорливому — совету экспертов), и единственная общая инструкция —
про последнюю строку с ответом. Она про форму, а не про способ думать: без неё
«прямой ответ без инструкций» перестал бы им быть, а ответы не с чем было бы сверять.

У «промпта от модели» два запроса на прогон: сначала модель пишет промпт под задачу,
потом решает по нему. В первом запросе ей прямо запрещено решать — иначе она
приносит готовый ответ прямо в промпте, и второй запрос уже не рассуждает,
а переписывает. Экран считает запросы заранее: пять прогонов — это 25 обращений
к API, а не 20.

Совет экспертов показывает не только итог: у каждого эксперта своя строка `ВЫВОД:`,
поэтому видно, сошлись они или разошлись. Состав совета редактируется прямо на
экране — три роли по умолчанию только заготовка.

Верный ответ вписывать необязательно: без него вердикта не будет, но способы всё
равно сравниваются между собой — сошлись ли они на одном ответе. Зато тип задачи
ограничен: лаборатория берёт только задачи с одним проверяемым ответом, на всё
остальное модель во всех четырёх режимах отвечает `ОТВЕТ: ОТКАЗ`.

Промпты, разбор ответа и сверка с эталоном живут в
[Reasoning.kt](core/src/commonMain/kotlin/com/mau89/talkloop/llm/Reasoning.kt)
и покрыты тестами без обращения к сети. Те же четыре способа в консоли,
по одному прогону и с полными ответами рядом: `./gradlew :cli:day3 -q --console=plain`.

### Вкладка «Температура» — случайность ответа

Один и тот же запрос уходит в модель с `temperature = 0`, `0.7` и `1.2`, каждый —
по нескольку раз. Запрос любой — сравнение точности, креативности и разнообразия
остаётся на глаз; автоматически считается только расхождение ответов между
прогонами одной температуры.

| temperature | Точность | Креатив | Разнообразие |
|---|---|---|---|
| 0 | факт стабилен | идеи схожие | ответы почти одинаковые |
| 0.7 | баланс | умеренная вариативность | иногда разные идеи |
| 1.2 | факт может плыть | смелее, неожиданнее | больше уникальных ответов |

У Anthropic Messages API диапазон temperature — 0..1, поэтому значение 1.2 из
задания уходит в запрос как 1.0 (максимум провайдера).

Когда что брать:
- **0** — факты, классификация, извлечение данных, код по шаблону;
- **0.7** — диалог, объяснения, черновики;
- **1.2** — названия, слоганы, сюжеты — где важнее новизна, чем повторяемость.

Промпты и подсчёт разнообразия живут в
[Temperature.kt](core/src/commonMain/kotlin/com/mau89/talkloop/llm/Temperature.kt)
и покрыты тестами без обращения к сети. Те же три температуры в консоли:
`./gradlew :cli:day4 -q --console=plain`.

### Вкладка «Модели» — слабая, средняя, сильная

Один и тот же запрос уходит в три точки линейки Anthropic — аналог «начала,
середины и конца» [каталога Hugging Face](https://huggingface.co/inference/models):

| Класс | Модель | Цена / 1M ток. (in / out) | Когда брать |
|---|---|---|---|
| слабая | `claude-haiku-4-5` | $1 / $5 | массовые короткие запросы, классификация |
| средняя | `claude-sonnet-5` | $2 / $10 | повседневный диалог и разбор |
| сильная | `claude-opus-5` | $5 / $25 | сложные рассуждения, цена ошибки выше цены токенов |

Замеряются время ответа, входные и выходные токены и оценка стоимости по
[тарифу Anthropic](https://platform.claude.com/docs/en/about-claude/pricing).
Качество сравнивают на глаз: верный ответ вписывать необязательно. Если
вписать — появится сверка (для примера про улитку это `8`; ловушка —
`10 / (3 − 2) = 10`). `max_tokens` один на всех. Temperature в запрос не
кладём: у Sonnet 5 и Opus 5 параметр снят (вместо него adaptive thinking),
а 400 на одной модели сломал бы сравнение.

Пресеты, оценка стоимости и форматирование метрик живут в
[ModelVersions.kt](core/src/commonMain/kotlin/com/mau89/talkloop/llm/ModelVersions.kt)
и покрыты тестами без обращения к сети. Те же три модели в консоли:
`./gradlew :cli:day5 -q --console=plain`.

### День 6 — первый агент

Во вкладке «Агент» запрос не отправляется из UI напрямую. Отдельная
сущность [TalkLoopAgent](core/src/commonMain/kotlin/com/mau89/talkloop/llm/TalkLoopAgent.kt)
инкапсулирует полный цикл: пропускает реплику через input policies, добавляет
накопленный контекст, вызывает `LlmClient`, применяет output policies и при
необходимости передаёт результат judge. Новая пара сообщений сохраняется только
после успешного прохождения всех этапов.

[AgentConfig](core/src/commonMain/kotlin/com/mau89/talkloop/llm/AgentConfig.kt)
задаёт модель, системный промпт, лимиты, политики и judge отдельно для каждого
логического агента. [AgentRuntime](core/src/commonMain/kotlin/com/mau89/talkloop/llm/AgentRuntime.kt)
использует один общий `AnthropicLlmClient` и создаёт любое количество независимых
агентных сессий со своими конфигурациями, историями и `Mutex`. Поэтому 100 агентов
не означают 100 сетевых клиентов; реальное число одновременных API-вызовов всё
равно должно учитывать rate limit провайдера.

`AnthropicLlmClient` остаётся общим HTTP-адаптером, а Compose отвечает только за
ввод и отображение результата. Под полем ввода мелким текстом показывается число
созданных runtime-агентов, выполненных LLM-запросов, а также входных, выходных и
суммарных токенов текущего агента.

Во вкладке «Агент» конфигурацию можно менять без правки кода: доступны системный
промпт, модель, temperature и max tokens. Кнопка «Создать нового агента» создаёт
в том же runtime новую независимую сессию с пустой историей, не создавая новый
HTTP-клиент.

### День 7 — сохранение контекста

После каждого успешно принятого ответа `TalkLoopAgent` сохраняет всю подтверждённую
историю через `ChatHistoryStore`. Реализация `JsonChatHistoryStore` сериализует
версионированный документ с массивом `messages`; Android хранит эту JSON-строку
в приватных `SharedPreferences`, iOS — в `NSUserDefaults`. При создании нового
экземпляра агент загружает документ до первого запроса, а экран получает сообщения
из того же `StateFlow`, поэтому показанный и отправляемый модели контекст совпадают.

Сбой API, input/output policy или judge не оставляет половину диалога: новая пара
появляется в оперативной истории только после успешной постоянной записи. Повреждённый
JSON безопасно трактуется как пустая история. Тесты имитируют перезапуск двумя
экземплярами агента с одним хранилищем и проверяют, что второй запрос содержит реплики
первого запуска.

Практическая проверка во вкладке «Агент»:

1. Напишите: `Меня зовут Маша` и дождитесь ответа.
2. Полностью закройте и снова запустите приложение.
3. Напишите: `Как меня зовут?` — агент получит предыдущие сообщения вместе с вопросом.
